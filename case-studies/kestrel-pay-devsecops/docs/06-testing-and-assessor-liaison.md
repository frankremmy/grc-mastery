# 06 — Pen testing, scanning schedule and assessor liaison

## Security testing calendar

| Activity | Frequency | Trigger | Requirement | Owner |
|---|---|---|---|---|
| SAST, SCA, secret scan | Every PR plus weekly scheduled re-scan | Code change; new CVE published | PCI DSS 6.2.4, 6.3.1 | DevOps (pipeline), ISO (rules) |
| DAST (ZAP baseline) | Every merge to main | Deployment | PCI DSS 6.4 / 11.3 | DevOps |
| Internal vulnerability scan | Quarterly, and after significant change | Calendar | PCI DSS 11.3.1 | ISO |
| External ASV scan | Quarterly | Calendar | PCI DSS 11.3.2 | ISO, with the approved scanning vendor |
| Application and network pen test | Annually, and after significant change | Calendar; major release | PCI DSS 11.4 | ISO, with the external tester |
| Segmentation test | Annually (6-monthly if Kestrel is assessed as a service provider) | Calendar | PCI DSS 11.4.5–11.4.6 | ISO |

## Pen test brief for the refund service (extract)

What the scanners can't cover goes to the human tester:
- **Business logic:** refund limits, refund higher than the original transaction, replaying the same refund request (T5).
- **Authorisation:** cross-tenant access by changing merchant identifiers in every parameter and header (T2).
- **Authentication:** API key handling and rate limiting.
- **Rules of engagement:** test environment only, test PANs only, named contacts, stop conditions, and evidence handling (findings sent only through the encrypted portal).

**How I'd run the assessor relationship:**
- One tracker and one point of contact.
- Evidence is generated by the pipeline, not screenshotted on the day.
- Gaps are disclosed early, with the corrective action and its date, rather than discovered by the assessor. That's the "no surprises" rule from the auditee's side.
