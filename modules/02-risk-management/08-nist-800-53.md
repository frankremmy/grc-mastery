# NIST and the SP 800-53 control catalogue

> Module 02, lesson 8. Where controls come from when you need a comprehensive
> list rather than a principle.

## Summary

NIST — the National Institute of Standards and Technology — isn't a framework. It
publishes a large body of standards and guidelines, several of which matter to
this work. The one this lesson points at is **SP 800-53**, a catalogue of security
and privacy controls that organisations select from to manage cyber risk.

This is the concrete answer to lesson 5's point that control selection isn't
improvisation. Faced with an assessment, you don't invent safeguards — you go to a
catalogue that already covers the ground. 800-53 is the comprehensive end of that
spectrum: Revision 5 runs to 20 control families, 322 base controls, and 1,189
rows once control enhancements are counted.

The lesson's worked example is **AC-17, Remote Access**, which is a good one given
how much work is now done from home. The control itself requires establishing and
documenting usage restrictions and connection requirements for each type of remote
access, and authorising each type before allowing it. The specific safeguards that
implement it are the familiar ones: multi-factor authentication, password
strength requirements, VPN.

The instruction is to read it, not memorise it. It's a reference document — the
kind you return to for years rather than learn once.

## How the catalogue is structured

Each row carries a control identifier, the control name, the control text, a
discussion section explaining intent, and a list of related controls.

The 20 families, by prefix:

| | | | |
| --- | --- | --- | --- |
| AC — Access Control | AT — Awareness and Training | AU — Audit and Accountability | CA — Assessment, Authorization and Monitoring |
| CM — Configuration Management | CP — Contingency Planning | IA — Identification and Authentication | IR — Incident Response |
| MA — Maintenance | MP — Media Protection | PE — Physical and Environmental Protection | PL — Planning |
| PM — Program Management | PS — Personnel Security | PT — PII Processing and Transparency | RA — Risk Assessment |
| SA — System and Services Acquisition | SC — System and Communications Protection | SI — System and Information Integrity | SR — Supply Chain Risk Management |

The families map closely onto the rest of this course — IR is module 8, SR is
module 9, RA is this module, AT is module 6.

## Key concepts

| Concept | What it means | Why it matters in practice |
| --- | --- | --- |
| NIST | A US standards body publishing many guidelines, not a single framework | "We follow NIST" is an incomplete sentence — which publication? |
| SP 800-53 | A catalogue of security and privacy controls | The comprehensive reference for control selection |
| Control | A safeguard that removes a risk, or reduces its likelihood or impact | The same definition used since lesson 3, now with a source |
| Control family | A grouping of related controls under a two-letter prefix | How you navigate 1,189 rows without reading them all |
| Control enhancement | A stronger or more specific variant of a base control, written as AC-17(1) | Lets a control be applied at different levels of rigour |
| Related controls | The cross-references attached to each control | Shows that controls work as a set, not individually |
| Reference document | Something consulted repeatedly, not memorised | Sets the right expectation for how to study it |

## Where this shows up in a real job

The remote access example isn't hypothetical for me — Automattic is fully
distributed, so every working day happens over exactly the controls AC-17
describes. I've experienced that estate as a set of individual requirements
(authenticate this way, connect through that). Seeing them as one named control
with a documented intent behind them reframes the friction as a design.

The closer parallel is ISO 27001 Annex A from the Helium Health work. Same idea —
a published catalogue you select from and justify against — at a different scale
and for a different purpose. Knowing one makes the other legible, which is
probably the most transferable thing about learning any control catalogue.

The `SR` family is the one I'd read first, because supply chain is where the
WordPress work and the CVE lab already live.

## My take

Two things became obvious only from opening the spreadsheet rather than reading
about it.

**The control text is full of blanks on purpose.** Controls read like
"[Assignment: organization-defined frequency]" — the catalogue deliberately
doesn't tell you how often to review access or how long to retain logs. It tells
you that you must decide, and having decided, write it down. That's more demanding
than a checklist, and it's the part that makes a control auditable: the auditor
checks you against your own stated parameter.

**The catalogue is a graph, not a list.** AC-17 alone cross-references nineteen
other controls. You cannot implement remote access as an isolated item — it pulls
in account management, identification and authentication, configuration
management, monitoring. That's defence in depth from the previous lesson, encoded
as structure.

The thing I want to avoid is treating 1,189 rows as a to-do list. Nobody applies
all of them; that's what baselines are for, and what the risk assessment is for.
The catalogue tells me what a control should look like and gives my recommendation
a reference anyone can check. It doesn't tell me which risk matters most — that
still comes from the assessment, and getting that backwards produces an enormous
amount of paper and not much security.

## Reference

A copy of the catalogue lives at
[`../../reference/sp800-53r5-control-catalog.xlsx`](../../reference/sp800-53r5-control-catalog.xlsx)
so the families and control text are to hand while working through the modules.

It's Revision 5 as supplied with the course. NIST ships 800-53 as patch releases
against Rev 5 rather than new revision numbers, and the current one is **Release
5.2.0** (August 2025), which adds controls around software update and patch
integrity. Fine to learn the structure from the copy here; anything that goes into
a deliverable should cite the current release, pulled from NIST's Cybersecurity
and Privacy Reference Tool.
